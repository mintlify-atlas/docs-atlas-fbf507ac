TimeFlow follows the **Model-View-ViewModel (MVVM)** architecture pattern recommended by Google for Android. Data flows in one direction — from the database up through repositories and a shared ViewModel to the Compose UI — keeping each layer testable and independent.

## Data flow

```
Room DB / DataStore
       ↓
  Repository
       ↓
 TaskAndEventViewModel  (StateFlow / State)
       ↓
 Compose screens  →  user action  →  ViewModel function  →  Repository
```

The ViewModel holds all mutable state. Screens are stateless — they observe flows and call ViewModel functions in response to user input.

## Package structure

```
com.dev.timeflow/
├── Data/           # Entities, DAOs, databases, repositories
├── Di/             # Hilt application class and module
├── Managers/       # AlarmManager services, notification receiver, boot receiver
├── View/           # Compose screens, navigation, widgets, theme, utilities
└── Viewmodel/      # TaskAndEventViewModel
```

## Dependency injection with Hilt

TimeFlow uses **Hilt 2.56.2** to wire the dependency graph. `Application.kt` is annotated with `@HiltAndroidApp` and `TimeflowModule.kt` provides:

- Both Room database instances (`TaskDatabase`, `EventDatabase`)
- DAOs (`TaskDao`, `EventDao`)
- Repositories (`TaskRepo`, `EventRepo`, `DataStoreRepo`)
- The `DataStore<Preferences>` instance

`TaskAndEventViewModel` is annotated with `@HiltViewModel` and injected into every Compose screen via `hiltViewModel()`. All screens share a single ViewModel instance scoped to the activity.
